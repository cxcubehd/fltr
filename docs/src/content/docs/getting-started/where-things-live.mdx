Everything public is in one flat namespace, `fltr`. There is no per-subsystem
nesting: `fltr::Row`, `fltr::RenderFlex` and `fltr::GestureArena` all sit
together. The directory structure reflects dependency order, not naming.

## The one header you always need

`fltr/widgets/binding.hpp` is the entry point: it declares `WidgetBinding`, which
owns the three trees and runs the three phases. It pulls in `widgets/basic.hpp`,
so the widget catalogue comes with it.

## Two exceptions

The layout has a rule: a directory only depends on directories below it. It gets
broken twice, both times because the alternative was worse.

<Aside type="note" title="RenderPointerRegion lives in gestures/, not render/">
It is a render object, but the only one that knows the gesture layer exists.
Putting it in `render/` would make the entire render tree depend on `gestures/`.
Instead `RenderBox` exposes one virtual hook, `asPointerRegion()`, which returns
non-null for exactly one class, and that class lives with the subsystem it
serves. Same reasoning for `RenderViewport` and `RenderScrollbarThumb` in
`scroll/`.
</Aside>

<Aside type="note" title="harness.hpp sits at the top level">
It is not a subsystem; it reaches into all of them. Every function in it takes a
tree or a list and returns a `std::string`, and nothing in the framework depends
on it.
</Aside>

## Other namespaces

| Namespace | What is in it |
|---|---|
| `fltr` | Everything public |
| `fltr::Curves` | The easing constants: `linear`, `easeIn`, `easeOut`, `easeInOut`, and the cubic variants |
| `fltr::dbg` | `str(...)` overloads for the geometry types, used by the harness dumps |
| `fltr::detail` | Internal. The contract-violation handler is the only thing here a consumer touches. |
