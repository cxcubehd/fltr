## The four load-bearing invariants

`DESIGN.md:13`. These are the reasons for choosing Flutter's architecture in the
first place, and nothing below them is negotiable without a redesign.

<div class="sl-flex" />

1. **Immutable config / persistent element / render object.** Declarative
   authoring stays compatible with incremental update because the thing the game
   code writes is not the thing that persists and not the thing that lays out and
   paints.
2. **Constraints down, sizes up, single pass.** A child cannot see its parent's
   size. This is what makes layout linear rather than iterative.
3. **Relayout and repaint boundaries.** Update cost is proportional to the dirty
   set rather than the tree, and layout invalidation and paint invalidation are
   separate paths with separate dirty lists.
4. **Gesture arena.** Overlapping interactive regions resolve deterministically.

Covered here: [Invariants and sharp edges](/fltr/architecture/invariants/).

## The build prompts

Two more documents in the repository root:

**`INSTRUCTIONS.md`** is the original brief for phase one. The rule that has shaped
the catalogue ever since is here: add widgets when a target screen needs them, not
speculatively.

**`INSTRUCTIONS2.md`** is the phase-two plan. Two sections are worth reading:

- **"The gaps, stated plainly"** (`:63`): the six things missing after M8, written
  before any of them were built. Comparing that list to the
  [findings page](/fltr/project/gaps-and-rework/) is the clearest picture of what
  phase two actually closed.
- **"Candidate workstreams"** (`:167`): A through M, of which A–E and J were
  committed as M9–M14. The letters referenced throughout the findings page are
  these: **F** is `LayoutBuilder` and lazy children, **H** is text spans and
  ambient style, **I** is the layout catalogue, **K** is ambient view metrics,
  **M** is text editing.

## What the docs do not carry over

`DESIGN.md` records what is verified at the end of each milestone: the exact tests
and what each one asserts. That belongs with the source rather than the consumer
documentation, and it is the best reading in the file if you want to know how
seriously a claim was checked.

Two examples, quoted verbatim:

> A frame of exit animation builds nothing and allocates nothing.

> The retained subtree keeps ticking (a number it accumulated on its own after it
> was removed) and stops when it is finally discarded.

The suite is 376 tests and 2,077 checks, green on GCC 13.3 and Clang 18.1 under
`-Wall -Wextra -Wpedantic -Wshadow -Wnon-virtual-dtor`, and under ASan + UBSan. The
library also compiles clean with `FLTR_ENABLE_CHECKS=OFF`.
