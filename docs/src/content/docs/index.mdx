## What it is

A UI framework you embed in a game engine. It does not own the window, the input
system, the GPU, or the clock. You push state in, call one function per frame, and
get back an ordered list of drawing commands to translate.

```cpp
// Once.
MyTextService text;
fltr::WidgetBinding binding({1280, 720}, text);
binding.attachRoot([&] { return hud(state); });

// Every frame.
for (const auto& event : platformEvents) binding.dispatchPointer(event);
const fltr::Scene scene = binding.drawFrame(deltaSeconds);
submit(*scene.root);
```

A frame in which nothing changed builds nothing, lays out nothing and paints
nothing, and hands back a scene whose `revision` has not moved. You can resubmit
last frame's translation verbatim.

## The four load-bearing ideas

Most of fltr is negotiable. These four are not, and the rest of the design is
arranged around keeping them true.

<CardGrid>
  <Card title="Three trees, three lifetimes" icon="seti:cpp">
    What you write (a widget) is not what persists (an element) and not what lays
    out and paints (a render object). That split is what makes declarative
    authoring compatible with incremental update.
  </Card>
  <Card title="Constraints down, sizes up" icon="puzzle">
    A parent hands a child constraints; the child answers with a size. A child
    never sees its parent's size. Layout is one linear pass, not a solver.
  </Card>
  <Card title="Boundaries, not trees" icon="approve-check">
    Layout invalidation and paint invalidation are separate paths with separate
    dirty lists. Update cost is proportional to what changed rather than to how
    big the tree is.
  </Card>
  <Card title="A gesture arena" icon="rocket">
    Overlapping interactive regions resolve deterministically, and a recognizer
    keeps receiving events after the pointer has left the region it started in.
  </Card>
</CardGrid>

## What it is not

There is no renderer, no font loader, no window, no navigator, no accessibility
tree and no theme system. Some of those are the consumer's job; some are gaps.
The [findings page](/fltr/project/gaps-and-rework/) says which is which.
