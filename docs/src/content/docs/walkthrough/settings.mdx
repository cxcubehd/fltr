Two switches and a slider, wired to fullscreen, vsync and the frame cap. This is
where the component layer stops being a button and starts being a control surface.

## The switch

`RawToggle` is the one machine behind a checkbox, a switch and a radio. What makes
it a *switch* is one number.

```cpp title="docs/demo/src/ui/widgets/toggle_row.cc"
  return RawToggle::make({
      .key = spec.key,
      .value = spec.value ? ToggleValue::On : ToggleValue::Off,
      .onChanged = spec.onChanged,
      // A non-zero drag extent is what makes this a switch rather than a
      // checkbox: it creates the drag recognizer, and the thumb follows the
      // finger instead of jumping when it is let go.
      .dragExtent = travel,
      .enabled = spec.enabled,
      .autofocus = spec.autofocus,
      .child = ...
  });
```

`dragExtent = 0` creates no drag recognizer at all, which is a checkbox. A non-zero
one means a drag of that distance moves the position end to end, and letting go
past halfway reports the toggle.

That distance is about twenty pixels, which is the whole reason a switch is where
a drag's slop shows up first. A finger's slop is eighteen, so holding a mouse to
it would leave the thumb still until the pointer had passed the far end -- and the
component starts its drag where the drag was *recognized* rather than where the
pointer went down, so the travel the arena swallowed is never replayed as a jump.
Both are what Flutter's `Switch` does, and it is a switch that makes the reasons
visible.

### The thumb

The component publishes a 0..1 fraction. `MappedValue` turns it into a translation.

```cpp title="docs/demo/src/ui/widgets/toggle_row.cc"
Transform2D slideX(float fraction, float travel) noexcept {
  return Transform2D::translation({fraction * travel, 0.0f});
}

WidgetRef SwitchThumbState::build(BuildContext& context) {
  travel_.bind(ComponentScope::fractionOf(context), &slideX, widget().args().travel);

  return fltr::Transform::make({
      .animation = &travel_,
      .origin = Alignment::centerLeft(),
      .child = DecoratedBox::make({
          .decoration = {.color = widget().args().color,
                         .radius = BorderRadius::all(widget().args().diameter * 0.5f)},
          .child = SizedBox::make({.size = fltr::Size::square(widget().args().diameter)}),
      }),
  });
}
```

Dragging the thumb repaints one render object and rebuilds nothing, through the
whole drag, at whatever rate the pointer reports.

While dragging, the component pins the position rather than animating to it: the
thumb is following a finger, not a clock. Letting go animates it home over
`positionDuration`.

### The track

The track is a `StyledSurface` with pill radii, so it picks up hover, press, focus
and disabled from the same machinery every button uses:

```cpp title="docs/demo/src/ui/widgets/toggle_row.cc"
  SurfaceStyle track = trackStyle(theme);
  const BorderRadius pill = BorderRadius::all(kTrackHeight * 0.5f);
  track.rest.radius = pill;
  track.hovered.radius = pill;
  track.pressed.radius = pill;
  track.selected.radius = pill;
  track.disabled.radius = pill;
  if (spec.value && spec.enabled) {
    track.rest.color = theme.accentSoft;
    track.rest.borderColor = theme.accent;
    track.hovered.color = theme.accentSoft;
    track.hovered.borderColor = theme.accent;
  }
```

<Aside type="note" title="Why the callback type is fltr's own">
```cpp
/// fltr's own signature, passed straight through: wrapping it in a
/// `Callback<void(bool)>` would nest one 32-byte inline closure inside
/// another, which `Callback` static-asserts against.
fltr::Callback<void(fltr::ToggleValue)> onChanged;
```

A nicer `bool` API would need a lambda capturing the caller's `Callback`: a 32-byte
object inside a 32-byte budget. It does not fit, and the static assert says so at
compile time.
</Aside>

## The slider

```cpp title="docs/demo/src/ui/widgets/slider_row.cc"
  WidgetRef track = RawSlider::make({
      .key = spec.key,
      .value = spec.value,
      .min = spec.min,
      .max = spec.max,
      .divisions = spec.divisions,
      .onChanged = spec.onChanged,
      // The value maps across the track less the thumb, so both ends stay
      // reachable -- the same number the visual uses for its travel.
      .thumbExtent = theme.px(14.0f),
      .enabled = spec.enabled,
      .child = SliderTrack::make({ ... }),
  });
```

The slider is the track and nothing else, and the label and the readout are
siblings of it rather than children. `RawSlider` reads the value off *where the
pointer is* inside its own box, so its box has to be the thing the player is
aiming at: wrapping the whole row would spread the range across the label and the
readout as well, leaving the visible track worth only the last third of it.

### Two views of one fraction

```cpp title="docs/demo/src/ui/widgets/slider_row.cc"
Transform2D scaleX(float fraction, float) noexcept {
  return Transform2D::scaling(std::clamp(fraction, 0.0f, 1.0f), 1.0f);
}

Transform2D slideX(float fraction, float travel) noexcept {
  return Transform2D::translation({std::clamp(fraction, 0.0f, 1.0f) * travel, 0.0f});
}

WidgetRef SliderTrackState::build(BuildContext& context) {
  const SliderTrack::Args& args = widget().args();
  const float travel = std::max(0.0f, args.width - args.thumbSize);

  fltr::ValueListenable<float>* fraction = ComponentScope::fractionOf(context);
  fill_.bind(fraction, &scaleX, 0.0f);
  thumb_.bind(fraction, &slideX, travel);
  ...
}
```

The fill is a full-width bar scaled about its left edge, which is what makes it a
fill rather than a zoom. It is a paint operation, so no layout runs while the
slider moves.

```cpp title="docs/demo/src/ui/widgets/slider_row.cc"
                  Align::make({
                      .child = ClipRect::make({
                          .radius = BorderRadius::all(args.thickness * 0.5f),
                          .child = fltr::Transform::make({
                              .animation = &fill_,
                              .origin = Alignment::centerLeft(),
                              .child = bar(args.fill),
                          }),
                      }),
                  }),
```

Dragging the slider repaints two render objects. Nothing rebuilds and nothing
lays out.

<Aside type="caution" title="Fixed width, because there is no LayoutBuilder">
```cpp
/// A fixed-width slider track. Fixed because the thumb's travel has to be known
/// when the mapping is set up, and fltr has no `LayoutBuilder` to ask the parent
/// how wide it ended up -- a real gap, recorded on the gaps page.
```

The travel has to be a number at build time. There is no way to ask "how wide did I
end up?" from a builder, so the width is passed in as `theme.px(180.0f)` and
`RawSlider::thumbExtent` is given the matching number by hand. Two constants that
must agree, with nothing enforcing it -- and both of them have to be scaled by
the same theme, which is one more place for them to disagree.

This is the most concrete missing capability the demo found. On the
[gaps list](/fltr/project/gaps-and-rework/).
</Aside>

### Absolute mapping

`RawSlider` maps the value absolutely from where the pointer is, rather than
accumulating drag deltas, so the thumb goes to the pointer on the first frame and
cannot drift over a long drag. There is no separate thumb hit region either,
because pressing anywhere on the track is already a press on the thumb.

## The screen

```cpp title="docs/demo/src/ui/screens/settings.cc"
                  // Only this subtree is rebuilt when a setting changes: the
                  // title, the rule and the frame around it are untouched.
                  Watch<GraphicsSettings>::make({
                      .value = &app.graphics(),
                      .builder = [&app](BuildContext& context,
                                        const GraphicsSettings& current) -> WidgetRef {
                        return graphicsPanel(app, ThemeScope::of(context), current);
                      },
                  }),
```

This is the case where a rebuild is genuinely the right answer: the labels change
(`"ON"` / `"OFF"`), and one control's `enabled` flips.

```cpp title="docs/demo/src/ui/screens/settings.cc"
                  toggleRow(theme,
                            {
                                .key = Key::of("settings.fullscreen"),
                                .label = "Fullscreen",
                                .hint = current.fullscreen ? "ON" : "OFF",
                                .value = current.fullscreen,
                                .onChanged =
                                    [&app](ToggleValue value) {
                                      GraphicsSettings next = app.graphics().value();
                                      next.fullscreen = value == ToggleValue::On;
                                      app.applyGraphics(next);
                                    },
                                .autofocus = true,
                            }),
```

```cpp title="docs/demo/src/ui/screens/settings.cc"
                  sliderRow(theme,
                            {
                                .key = Key::of("settings.fps"),
                                .label = "Frame cap",
                                .valueText = app.maxFpsText(),
                                .value = static_cast<float>(current.maxFps),
                                .min = 30.0f,
                                .max = 240.0f,
                                // Seven divisions is eight stops, 30 apart, and
                                // the component snaps for us -- the visual never
                                // sees an intermediate value.
                                .divisions = 7,
                                .onChanged = ...,
                                // The cap does nothing while vsync is driving
                                // the frame rate, so it says so by being off.
                                .enabled = !current.vsync,
                            }),
```

## Scaling the whole interface

The second panel is one more `sliderRow`, and what it changes is the theme
itself:

```cpp title="docs/demo/src/ui/screens/settings.cc"
  return panel(theme, EdgeInsets::all(theme.unit * 0.75f),
               sliderRow(theme, {
                                    .key = Key::of("settings.scale"),
                                    .label = "Interface scale",
                                    .valueText = app.uiScaleText(),
                                    .value = app.uiScale().value(),
                                    .min = 0.75f,
                                    .max = 2.0f,
                                    // Six stops, a quarter apart.
                                    .divisions = 5,
                                    .onChanged = [&app](float value) { app.setUiScale(value); },
                                }));
```

```cpp title="docs/demo/src/ui/root.cc"
WidgetRef buildRoot(App& app) {
  return Watch<float>::make({
      .value = &app.uiScale(),
      .builder = [&app](BuildContext&, const float& requested) -> WidgetRef {
        return Watch<float>::make({
            .value = &app.window().contentScale(),
            .builder = [&app, requested](BuildContext&, const float& density) -> WidgetRef {
              return themedTree(app, requested * density);
            },
        });
      },
  });
}
```

What the player asked for is a factor on top of what the display demands, which
is why the slider reads 100% on a fresh window however dense the screen is: a
device pixel ratio is the platform's business, not a setting. It is watched
rather than read because a display changes its mind -- a window dragged to
another monitor, a page zoomed -- and a tree measured in a ratio that moved is a
tree drawn at the wrong size.

This is the one thing in the demo that rebuilds everything, and it should:
`scaledTheme` multiplies the size tokens, so every size in the tree is a
different number afterwards. Doing it here rather than by drawing the finished
frame through a scaling matrix is what keeps text sharp -- the text service
rasterises an atlas per pixel size asked for, so a scaled theme asks for a
bigger one instead of stretching the one it has.

Note that this row is *not* wrapped in a `Watch`, unlike the graphics panel: the
value it displays is the one that just rebuilt the tree it is part of.

## The round trip

```cpp title="docs/demo/src/app/app.cc"
void App::applyGraphics(const GraphicsSettings& settings) {
  window_.apply(settings);
  syncGraphics();
}

void App::syncGraphics() {
  // Whatever the window actually did is what the settings screen shows -- the
  // readout included, which a platform that refuses a frame cap would otherwise
  // leave reading the number nobody honoured.
  if (window_.settings() == graphics_.value()) return;
  graphics_.set(window_.settings());
  formatMaxFps();
}
```

The observable is set from **`window_.settings()`**, not from the requested
value. `syncGraphics` is also called once a frame by the loop, because the answer
can arrive later than the request: a browser grants fullscreen to the gesture
that follows, and takes it back on Escape without telling anyone.

```cpp title="docs/demo/src/platform/window.cc"
void Window::apply(const GraphicsSettings& next) {
  if (!open_ || next == settings_) return;

  if (next.fullscreen != settings_.fullscreen) setFullscreen(next.fullscreen);

#ifndef __EMSCRIPTEN__
  if (next.vsync != settings_.vsync) {
    if (next.vsync) {
      SetWindowState(FLAG_VSYNC_HINT);
    } else {
      ClearWindowState(FLAG_VSYNC_HINT);
    }
  }

  if (next.maxFps != settings_.maxFps) SetTargetFPS(next.maxFps);
#endif

  settings_ = next;

#ifdef __EMSCRIPTEN__
  // A browser paces the frame itself, through the callback it drives the loop
  // with, and raylib's own wait is a suspend this build has no asyncify for.
  // Neither knob exists here, so neither is reported as having taken effect.
  settings_.vsync = true;
  settings_.maxFps = 0;
#endif

  // A fullscreen request is one a compositor may refuse and a browser answers
  // later, so the settings screen shows what happened rather than what was asked
  // for. `refresh` is what keeps showing it.
  refresh();
}
```

The web build is the case this design was waiting for. A browser will not be told
what to do with the frame rate, so on that platform the two knobs are simply not
applied -- and because the observable is fed from what the window ended up in,
the [demo running in a page](/fltr/demo/) shows vertical sync on and its frame
cap disabled without a single branch in the UI.

<Aside type="tip" title="The switch shows reality, not intent">
A compositor may refuse fullscreen. Because the observable is fed from what the
window ended up in, the switch snaps back on its own: no error path, no
reconciliation logic, just one value pushed and one `Watch` rebuilt.

That works because `Observable<T>::set` compares first: a request that succeeded
pushes the same value the toggle already showed and notifies nobody.
</Aside>

`apply` only touches what actually changed, because window calls are not free.
`GraphicsSettings` being equality-comparable is what makes that one line.

## The surface a page owns

`setFullscreen` is where the two platforms stop agreeing. A desktop window is
toggled and answers immediately; a browser is *asked*, grants fullscreen to a
gesture rather than to a frame, and revokes it on Escape without telling anybody.

```cpp title="docs/demo/src/platform/window.cc"
void setFullscreen(bool enter) {
  if (enter) {
    emscripten_request_fullscreen("#canvas", EM_TRUE);
  } else {
    emscripten_exit_fullscreen();
  }
}
```

Nothing there reports success, which is why `refresh` exists. It is called at the
end of `apply` and again by the loop every frame, and it answers three questions
the demo cannot infer: how large the drawing buffer should be, whether the
document is showing it full-screen, and how many of its pixels go into one of the
interface's.

```cpp title="docs/demo/src/platform/window.cc"
void Window::refresh() {
  if (!open_) return;
  refreshSurface();
  settings_.fullscreen = fullscreenNow();
  contentScale_.set(displayScale());
}
```

On a desktop `refreshSurface` is empty -- raylib's own window callbacks already
keep the buffer and the viewport in step. In a page it is the whole fix:

```cpp title="docs/demo/src/platform/window.cc"
void refreshSurface() {
  const fltr::Size wanted = pageSize();          // the CSS box times the pixel ratio
  if (wanted.isEmpty() || wanted == drawingBuffer()) return;
  SetWindowSize(static_cast<int>(wanted.width), static_cast<int>(wanted.height));
}
```

`SetWindowSize` rather than `emscripten_set_canvas_element_size`, because the
buffer is not the only thing that has to move with it: the same call resizes the
viewport and the projection, and it is what tells GLFW the pixels a mouse
position is measured in. A browser reports one in the page's pixels and GLFW
scales it by the ratio between the two, so a buffer resized behind its back is a
pointer that lands somewhere other than where it looks.

The comparison is against the buffer rather than against the last request for the
one case that needs it: GLFW answers the first resize made inside fullscreen with
the screen's CSS pixels, and asking again on the next frame is what settles it.

<Aside type="caution" title="raylib sizes a canvas in CSS pixels">
`InitWindow` leaves a resize handler behind that sets the drawing buffer to
`window.innerWidth` -- no pixel ratio anywhere in it. On a 2x display that is a
buffer the browser stretches to twice its size, which is a blurry page at 100%
and a UI drawn twice as large as its own settings claim. Registering another
handler does not help, because emscripten *adds* listeners rather than replacing
them; `adoptCanvas` removes raylib's, and the measurement above takes its place.
</Aside>

## The formatted value

```cpp title="docs/demo/src/app/app.cc"
void App::formatMaxFps() {
  const int cap = graphics_.value().maxFps;
  if (cap > 0) {
    std::snprintf(maxFpsText_, sizeof(maxFpsText_), "%d", cap);
  } else {
    std::snprintf(maxFpsText_, sizeof(maxFpsText_), "AUTO");
  }
}
```

```cpp title="docs/demo/src/app/app.hh"
char maxFpsText_[16] = "144";
```

The same pattern as the menu's best score, for the same reason: `Text` does not
copy its `string_view`.

<Aside type="note" title="Two gaps this screen hit">
Both components are complete: value, gestures, drag, keyboard, focus, disabled,
snapping. The demo supplied only pixels.

The missing `LayoutBuilder` forced a hardcoded slider width and two constants that
have to agree. And with no ambient view metrics, this screen knows the surface
size only because `App` happens to hold a `Window`.
</Aside>
